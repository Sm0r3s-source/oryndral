# Architecture and upstream research

Source review dated 9 November 2026. Upstream capabilities below are findings from source and project documentation. See the project README and benchmark record for Oryndral's verified support.

## Foundation decision

mistral.rs was evaluated first. Its Rust SDK loads local GGUF, converts tokenizer metadata, resolves chat templates and configures device mapping. Its public builder hands a complete pipeline to a scheduler and returns a model handle. The core owns the model, cache and placement. The inspected builder has no interface for releasing or reloading individual weights inside a forward pass. The core also includes vision, audio, and quantization crates. An Oryndral-specific weight provider would require changes inside that pipeline. [SDK builder](https://github.com/EricLBuehler/mistral.rs/blob/master/mistralrs/src/gguf.rs) · [GGUF pipeline](https://github.com/EricLBuehler/mistral.rs/blob/master/mistralrs-core/src/pipeline/gguf.rs) · [Core manifest](https://github.com/EricLBuehler/mistral.rs/blob/master/mistralrs-core/Cargo.toml)

Oryndral uses the Candle tensor stack that mistral.rs already uses. The lockfile pins Candle 0.11.1. Its GGUF reader exposes tensor shape, type and offset, plus a read operation that constructs the requested tensor on a chosen device. Its quantized operations and CPU/CUDA backends let Oryndral share the same forward pass across placements. Oryndral owns the transformer layer lifetime, KV state, placement and serving. The trade-off is narrower model coverage and a smaller set of scheduling and attention optimizations. [mistral.rs workspace manifest](https://github.com/EricLBuehler/mistral.rs/blob/master/Cargo.toml) · [Candle GGUF reader](https://github.com/huggingface/candle/blob/main/candle-core/src/quantized/gguf_file.rs) · [Candle quantized ops](https://github.com/huggingface/candle/blob/main/candle-core/src/quantized/mod.rs)

## Execution and memory ownership

- The GGUF file supplies metadata and a tensor index. The loader validates model geometry, required tensor shapes and file ranges before materializing weights. Embedding, final normalization and output projection sit on CPU. Candle supplies quantized matrix multiplication and embedding row lookup. When the output projection is tied to the embedding, both share the same weight storage. Llama GGUF query and key projections use adjacent-pair RoPE, matching the reference implementation. [llama.cpp RoPE kernel](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cpu/ops.cpp) · [Candle Llama reference](https://github.com/huggingface/candle/blob/main/candle-transformers/src/models/quantized_llama.rs)
- Resident execution loads all layers. The optional CUDA build implements a contiguous GPU suffix for hybrid execution, with each block's KV state following its device. Contiguous placement limits activation transfers per forward pass. The planner accounts for model tensors, KV state and an allowance for scratch space. Operating-system file cache, allocator overhead and other workloads can change observed memory use. CPU execution and placement calculations have local coverage. CUDA execution requires GPU verification.
- Dense streaming synchronously seeks to and reads one transformer layer into CPU memory, computes it, then releases its weight tensors. Each session holds KV independently of weights. Chunked prefill spreads each layer read across the tokens in that chunk. Single-token decode revisits every streamed layer for each step. With cold pages and no transfer overlap, reading `W` streamed bytes at sustained bandwidth `B` takes at least `W / B` seconds per decode step before compute. Logical read volume can be much higher than physical I/O when the OS serves repeated reads from memory.
- Expert streaming keeps attention, router and normalization weights resident. The router selects and normalizes the top experts for each token. CPU execution loads only those expert slices and can keep them in a byte-bounded cache keyed by `(layer, expert)`. LRU uses last access order. Optional LFU counts uses since admission and breaks ties by recency. Each token still computes its own routing weights. A cache hit reuses the expert matrices. The engine records cache hits, misses and GGUF payload bytes, which measure different quantities from physical storage traffic. The measured capacities and policies preserve identical completion tokens on the trained TinyStories MoE fixture.
- Tokenization uses the GGUF vocabulary and checks every token ID in an optional `tokenizer.json`. Legacy Llama SentencePiece merges are reconstructed from token scores and decoded with UTF-8 byte fallback. Tests compare fixed prompts with llama.cpp, including multiple spaces, newlines and an emoji. Equal-score and normalization edge cases need broader coverage. Candle supplies the Llama 3 byte-BPE path, which needs a model test. [llama.cpp tokenizer reference](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-vocab.cpp) · [Candle tokenizer](https://github.com/huggingface/candle/blob/main/candle-core/src/quantized/tokenizer.rs)
- The CLI and HTTP server share model loading, sampling and generation. MiniJinja renders supported embedded or supplied templates. A base model without a template accepts a single user message as a completion prompt. The loopback-only server loads one model at startup, admits one generation at a time and uses a bounded stream buffer. A streaming disconnect stops the worker at the next cancellation check between inference steps.

The SmolLM2-135M-Instruct Q4_K_M experiment capped committed process memory at 96 MiB with a Windows Job Object. The 105,454,144-byte GGUF generated the reference continuation in dense-stream mode. Resident loading failed an allocation under the same cap. The experiment limits process commit while leaving the machine's file cache available. [Benchmark record](benchmark.md) · [Windows process memory limit](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information)

## Server and Qwen2 expansion

Dense Qwen2 GGUFs reuse the existing decoder and placement code. They use split-half RoPE and can carry separate biases for the Q, K, V and attention output projections. The Qwen2 tokenizer profile uses Candle's byte-level BPE and validates the resulting vocabulary against the GGUF. Mythos-nano uses its embedded template and the model's chat end markers. Scaled RoPE, sliding-window Qwen2 layouts and Qwen expert models require additional execution work. [llama.cpp Qwen2 implementation](https://github.com/ggml-org/llama.cpp/blob/master/src/models/qwen2.cpp) · [Mythos-nano GGUF](https://huggingface.co/squ11z1/Mythos-nano-GGUF)

One worker owns the model, with a bounded queue for up to four waiting requests. Both completion routes use the same sampling, cancellation and stream lifecycle. The bundled browser chat uses the public API on the same origin.

Chat requests accept `chat_template_kwargs` (passed to the chat template as extra variables) and `reasoning_effort`. For a model whose tokenizer has `<think>` and `</think>` tokens, `enable_thinking: false` or `reasoning_effort: "none"` starts the reply after an empty reasoning block, so the model answers directly. Otherwise the server opens the reasoning block itself, which keeps reasoning out of the answer when the model would have skipped the opening tag. A template that already ends the prompt with a think tag is left alone. `/v1/models` reports `"reasoning": true` for such models. Tool calling is unsupported: a request with `tools` is rejected.

The Hugging Face client reuses the standard cache and accepts an explicit repository, revision and GGUF filename. [Hugging Face Rust Hub client](https://github.com/huggingface/hf-hub)

## Next validation milestones

1. Run Windows and Linux CPU CI plus model tests on pinned artifact hashes. Extend fixed-token tests to compare logits at multiple prefix lengths. Expand model coverage with one pinned instruct checkpoint per architecture and compare tokenizer and rendered chat-template output with the model's reference.
2. Measure dense streaming under a process limit with weights larger than available RAM. Record peak working set, bytes read, cold and warm first-token latency, and decode throughput. Compare against current llama.cpp mmap and explicit reads. Consider bounded double-buffering and mmap only after profiling the synchronous path.
3. Extend the verified Windows RTX 4050 result with CPU/CUDA logit tolerances, partial offload measurements, Linux testing and Pascal coverage. The GTX 1080 Ti has compute capability 6.1, and CUDA 13 removed offline compilation and library support for Pascal. A Pascal build needs a verified CUDA 12.x toolchain and suitable kernels. [Windows CUDA verification](benchmark.md#windows-cuda-verification) · [NVIDIA legacy compute capabilities](https://developer.nvidia.com/cuda/gpus/legacy) · [CUDA 13 release notes](https://docs.nvidia.com/cuda/archive/13.0.0/cuda-toolkit-release-notes/index.html#deprecated-architectures)
4. Extend expert routing and fixed-token comparisons to a larger MoE checkpoint. Replay routing traces to compare LRU, LFU and prefetch using equal memory budgets, held-out prompts and cold and warm caches. Add GPU promotion only after measured transfer and compute savings. Count evictions, prefetched bytes used, and time per token.
5. Measure attention and scheduling bottlenecks at representative context lengths before enabling paged or prefix KV caching, continuous batching, speculative decoding, or fused attention. Report upstream comparisons with the same model bytes, context, prompt, output length, sampling, cache state and hardware wherever supported.
